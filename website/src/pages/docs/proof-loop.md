## The claim that is tested

Every migration makes a claim: *if you run me on an older database, you get the schema the application needs.* Most tools trust that claim. MIG-Ace tests it in every build.

## The six steps

**1. Build schema A, the expected schema.**
MIG-Ace runs the files in your [schema folder](/docs/desired-schema/) on an empty PostgreSQL database. One of these files is generated by Hibernate from your entity classes.

**2. Load schema B, an older release.**
MIG-Ace loads a baseline: the database of an earlier release, with data in it.

**3. Migrate B.**
The migration script runs on B. After each snippet, the snippet's [test data](/docs/test-data/) is inserted, so that later snippets work on filled tables.

**4. Compare A and B.**
Tables, columns, types, constraints, indexes, sequences, views and functions must be the same.

**5. Run the script again.**
A second run must change nothing. This shows that the script can be repeated safely.

**6. Install on an empty database.**
The same script runs on an empty database, where it [installs the schema directly](/docs/first-run/). The result must equal A as well. A new customer and an upgraded one get the same database.

```text
$ mig test

schema A    built from schema/                 ok
schema B    release 1.0.0 with data loaded     ok
migrate     2 snippets, 7 parts                ok
test data   customer, review                   ok
compare     A = B, no differences              ok
run again   nothing left to do                 ok
install     empty database, A = installed      ok
```

## What a failure looks like

**A statement fails on data.** The entity says the column is mandatory, but the snippet gives existing rows no value.

```text
migrate     20260302-0900-customer-loyalty
  ✗ part make-mandatory failed on release 1.0.0
    ERROR: column "loyalty_level" of relation "customer" contains null values
```

**The result differs from what Hibernate expects.** The entity says `length = 20`, the snippet says `varchar(10)`.

```text
compare     1 difference
  customer.loyalty_level
    expected (schema/)       varchar(20)
    migrated (snippets)      varchar(10)
```

**Something is missing.** A developer added a field to an entity and wrote no snippet.

```text
compare     1 difference
  book.isbn
    expected (schema/)       varchar(17)
    migrated (snippets)      column does not exist
  Run "mig make" to create a snippet for this difference.
```

In all three cases the build fails. Nothing has reached a real database.

## Baselines: where the migration starts

A baseline is the database of one release, with data and with its ledger. The ledger tells MIG-Ace which snippets that release already contains, so only the missing ones are applied.

MIG-Ace tests every release you still support as a starting point. For the bookshop:

```text
$ mig test

from 1.1.0   6 snippets to apply    A = B   ok
from 1.1.1   5 snippets to apply    A = B   ok
from 1.2.0   2 snippets to apply    A = B   ok
```

This matters because the three stores are on three different releases. Harbour Books will jump from 1.1.1 straight to 1.3.0, and the proof covers exactly that jump.

You do not have to store a database dump for every release. MIG-Ace can rebuild a baseline from the release tag in git and fill it with the test data that existed then. Add a real, anonymised dump where the shape of real data matters.

## The temporary database

The proof loop needs a PostgreSQL to work in. MIG-Ace starts its own for the duration of the build and removes it afterwards.

- No Docker is required.
- It works on locked-down company laptops and inside CI containers.
- It uses the same major PostgreSQL version as your production database, which you set in `migace.yaml`.

If your build machine may not start programs, you can point MIG-Ace at a PostgreSQL server instead. It then creates two temporary schemas there. Both choices are settings of your own computer, see [Configuration](/docs/configuration/).

## Faster feedback

The full loop over all baselines runs in CI. While you work on a snippet, a shorter form is enough:

```text
$ mig test --from 1.2.0
```

The [editor](/docs/editor-support/) goes further and checks each statement as you type.

## What the proof does not cover

The proof loop shows that the schema is right and that every statement runs on the test rows. It cannot know whether a data change is *meant* the way you wrote it. For that you state your intent with [`verify-after`](/docs/data-migrations/) and provide [test rows](/docs/test-data/) that look like real data.
