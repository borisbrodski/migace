## The idea

Your application has entity classes. Hibernate can turn them into `create table` statements. That is the schema your application **expects**.

Your production database was created long ago and has changed many times since. That is the schema you **have**.

A migration is the set of statements that turns the second into the first. MIG-Ace **writes** most migrations for you and **proves** every one of them:

1. It builds the expected schema in an empty PostgreSQL database.
2. It loads an older release of your database, with data, into a second one.
3. It runs your migrations on the second one.
4. It compares the two. They must be identical.

This comparison is called the [proof loop](/docs/proof-loop/). It runs in every build, on the developer's machine and in CI.

The same comparison also works the other way round. When the two differ because you changed an entity, `mig make` turns the difference into a [generated snippet](/docs/generated-snippets/).

## The parts

| Part | What it is | Read more |
|---|---|---|
| Schema folder | SQL files that create the expected schema. One of them is generated by Hibernate. | [The desired schema](/docs/desired-schema/) |
| Snippets | Small YAML files, one per change. Each has named parts, and each part is one statement. | [Snippets](/docs/snippets/) |
| `mig make` | The command that writes snippets from the difference between the expected schema and your migrations. | [Generated snippets](/docs/generated-snippets/) |
| Editor support | A language server that knows your schema and completes tables, columns and keywords. | [Editor support](/docs/editor-support/) |
| Views, functions and triggers | Kept in the schema folder and replaced by every run. No snippets needed. | [Views, functions and triggers](/docs/views-functions-triggers/) |
| Test data | Rows that a snippet brings along, so it is tested on tables that are not empty. | [Test data](/docs/test-data/) |
| Proof loop | The build step that migrates an older database and compares the result. | [The proof loop](/docs/proof-loop/) |
| Migration script | One SQL file, produced by the build, that contains all snippets. This is what you run in production. | [Running migrations](/docs/running-migrations/) |
| Ledger | Tables in your database that record every part that ran, when, and with what result. | [Running migrations](/docs/running-migrations/) |
| Fingerprint | A hash of the schema. The application checks it at start-up. | [The desired schema](/docs/desired-schema/) |
| Release files | A small file per release that remembers what was shipped. | [Releases and branches](/docs/releases-and-branches/) |

## What a snippet looks like

A snippet is a YAML file. The statements inside it look like the SQL you already know.

```yaml
# migrations/20260302-0900-customer-loyalty.migql.yaml
migration: 20260302-0900-customer-loyalty
uid: 01JF2A6QW3ZK8M4T7R9B5X0C1D
doc: Every customer gets a loyalty level

parts:
  - add-column:
      do: alter table customer add column loyalty_level varchar(10)

  - fill-existing:
      do: update customer set loyalty_level = 'BRONZE'

  - make-mandatory:
      do: alter table customer alter column loyalty_level set not null
```

The script that MIG-Ace builds from your snippets can be run again and again. Parts that already ran are skipped, so a run that stopped halfway simply continues.

## What happens in production

1. The build produces `migration-script-pg.sql` and puts it into your JAR.
2. Your application runs it at start-up with one line of Java, or you run it as a separate step before deployment.
3. At the end, the script reads the real schema, computes its fingerprint and compares it with the expected one.
4. An application that finds the wrong schema refuses to start.

All migration logic is in the script. The Java library only sends it to the database.
