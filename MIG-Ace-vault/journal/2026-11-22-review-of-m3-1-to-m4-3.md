## Findings

### 1. A run can use the ledger of another schema — serious

The script puts the schema of the migration first in the search path and keeps what the session had. It looks for its ledger with `to_regclass('mig_meta')`, without the schema. When the schema of the migration has no ledger yet and a later schema of the path has one, the run takes that one.

Shown on PGlite with the bookshop in two schemas of one database, `public` and `tenant2`, and a session whose path ends with `public`:

1. The run on `public` creates the ledger in `public` and applies all parts.
2. The run on `tenant2` finds the ledger of `public`, reports every part as "already done", ends with "Nothing to do" and success. `tenant2` is unchanged and has no ledger. The run is recorded in `public.mig_run`.

A database with one schema per tenant, or two applications in one database, meets this. The run reports success and has done nothing.

The existing test of another schema (M4.1-AC-39) does not see it: no second ledger exists in that test.

This is also the answer the review proposes for question 46: every name the script uses for its own tables is bound to the schema of the migration, and the search path of a run is that schema alone. Other schemas, for the types of an extension, are named by a parameter.

### 2. Two names that differ only in case can have the same checksum

The checksum takes a keyword by its type, whatever its case. 26 keywords can be names without quotes since M3.1. For such a word the type is taken also when it is used as a name:

- `do: update t set value = 1` and `do: update t set Value = 1` have the same checksum, and so have `key` and `KEY`, `type` and `Type`. Under exact names these are different columns.
- An ordinary name is right: `price` and `Price` differ.

M4.1-AC-06 asks that a changed name changes the checksum. The property test does not build names from the list of keywords.

A way to correct it that stays with tokens: for a word that can be a name, its characters count, also where it is used as a keyword. The rule then says: the case of a keyword does not count, except for the words of the list in [Keywords and names](../migql/keywords.md). Rule `v1` is not released, so it can still be changed, and the committed list of checksums is written again once.

### 3. One server test depended on the place it ran in — corrected

`stopping it ends the process and removes the folder` asked at once whether the process was gone. A stopped process stays listed until the system removes its entry; in a container without a process that does this quickly, the test failed every time. The server was stopped correctly. The test now waits up to five seconds, as the test next to it does.

### 4. A run leaves its session changed, and after some failures locked

Found the same evening, while the spec for the corrections was written. Shown on PGlite with the bookshop script:

| | Search path of the session | Locks of MIG-Ace | Temporary functions |
|---|---|---|---|
| Before the run | `public` | 0 | 0 |
| After a good run | `shop, public` | 0 | 11 |
| After a failure at a statement outside a transaction | `shop2, public` | 1 | 11 |

The lock is released by a statement near the end of the script. When a statement outside a transaction fails, the runner stops, and that statement is never sent.

The Java library closes a connection that it took from a `DataSource`. With a pool, closing gives the session back to the pool, alive. A session that still holds the lock then blocks every later run on another connection, for as long as the pool keeps it. The changed search path and the functions go back to the application with the connection.

The tests could not see it: every test of a failure ended its session or released all locks itself afterwards.

## What worked

- **The design of the script holds.** An adapter of 127 lines in TypeScript and 151 in Java, with no knowledge of snippets, runs a script that records full errors, stops after a failure and continues at the right step. It was run on PGlite and on PostgreSQL 15 and 18, on three systems.
- **The killed-run test.** A connection lost after any of the 60 statements of the bookshop script, followed by a normal run, ends in the same model. This is the strongest statement about the script that exists so far.
- **The real server found what PGlite could not:** the deadlock between a waiting run and `create index concurrently`, and three problems of processes on Windows.
- **Mutation testing found what coverage hid.** The Java runner went from 85 % to 96 %. Breaking the SQL of the script by hand found one rule that no test held.
- **The session reported its own mistake.** The Java runner was not written test-first; the note says so, and the mutation run was the repair.

## What we learned

1. **A stored expected text proves that nothing changed, not that it is right.** The first attempt to break the script was "noticed" eleven times out of eleven, every time by the stored script. Tests of behaviour have to be counted apart.
2. **Defects sit where two decisions meet.** Finding 1 is the schema parameter meeting the kept search path. Finding 2 is exact names meeting a checksum by token type. Each decision was tested alone. A spec that changes a rule has to name the earlier rules it touches, and ask for a test of the pair.
3. **A test of "the other one is not touched" needs an other one that could be touched.** A second schema without a ledger, and names that are no keywords, could not show the two findings.
4. **The fingerprint differs between major versions of PostgreSQL**, because the text of a view is written differently. The proof loop has to run on the major version of production, and an application needs the fingerprint for that version.
5. **Copying a database costs 1.6 seconds on macOS** and 30 ms on Linux. A proof loop that copies a database for every step will be slow there.
6. **The package of binaries works on the three systems.** That removes the largest risk of "no Docker".

## Proposed answers to the open questions

They are proposals. The project owner decides.

| Question | Proposal |
|---|---|
| 45 Types of several words | Accept the forms of standard SQL: `double precision`, `timestamp with time zone`, `timestamp without time zone`, `character varying`. Needed before `mig make`, which writes the types that Hibernate creates. |
| 46 Search path | The schema of the migration alone. Other schemas by a parameter. See finding 1. |
| 47 `when` of a half-done part | Confirm: not asked again. A part that started has to end, or its helper objects stay. |
| 48 Skipped part and fingerprint | A skipped part is not pending; store the fingerprint. But the stored value is what the script expects, not what the database has. The script should compute the real fingerprint; plan it with the proof loop. |
| 49 Failure outside a transaction | Enough as it is. The next run says "abandoned" and repeats the step. |
| 50 Table in a lock failure | Enough as it is. |
| 51 Lock time limit outside a transaction | Try a session setting before the statement and its reset after. It needs no change of the contract. A test on a real server decides whether it limits the wait of `create index concurrently`. No retry in the same run. |
| 52 `ERROR: ` in Java | Keep the message of the driver. |
| 53 Package of binaries | Accept for the tests. Decide again before the first release, when users need binaries for the proof loop. |
| 54 Java tests in `npm test` | Take them out. `npm test` should need no network and no Gradle. `npm run test:java` stays, and the workflow runs it. |
| 55 Mutation run | Once a week in the workflow, on Linux, and by hand. No limit that fails a build until one full run exists. |
| 56 Condition on a later snippet | An error. A part that waits for a later one would run out of order on the next run. |
