# MigQL follow-up, schema model and PostgreSQL generation

Second implementation session. It covers M1.1, M2 and M3. The numbers are from a developer laptop with Linux and Node 22.22.2.

`npm run build`, `npm run lint` and `npm test` pass. No test needs Docker or a server: PostgreSQL runs as PGlite in the test process.

## M1.1

### Not proven yet: Windows

- The workflow now runs on Linux and on Windows, and it runs `npm run test:generate` and fails if a file changed afterwards (M1.1-AC-01, M1.1-AC-02).
- `.gitattributes` gives every text file LF line endings on every system (M1.1-AC-03). The lexer reads files with Windows line endings to the same tokens; a test proves it.
- **None of this has run on Windows.** The session had no Windows machine. The first push shows whether the Windows job is green.

### Choices

| Topic | Choice |
|---|---|
| A list of key columns in `upsert` | A YAML flow list: `key: [book_id, currency]`. The spec says "a list of columns" without a form. |
| Checks after a change (M1.1-AC-10) | After any change, linking and checks run again for every snippet of the project. No file is parsed again. This is simpler than finding the affected snippets, and it is correct. It has to be measured on a project with some hundred snippets. |
| A name in double quotes | The syntax tree keeps the quotes. The generator needs to know whether the author wrote them, because only then upper-case letters are kept. |
| A keyword that is also a value | `required` and `finish` became keywords (M1.1-AC-18). They are accepted as names, like `value` and `key`. `all` is not. |

### Loading a project

`loadProject(folder)` in `migql/src/project.ts` loads every `*.migql.yaml` below a folder, also in sub-folders, and returns all problems with file, line and column. Folders that start with a dot and `node_modules` are skipped.

## M2

### Design

- `core/src/schema/model.ts` is the model. `objects.ts` turns it into a flat list of objects with their properties as text. The canonical form, the comparison and the fingerprint all work on that list, so they cannot disagree.
- The canonical form is one block per object with one line per property. The fingerprint is the SHA-256 hash of it.
- A constraint or an index that is missing under one name and present under another, with the same definition in the same table, is reported as one difference with the property `name`.
- When a table is missing or unexpected, its columns and constraints are not listed again.

### The reader

- `databases/postgresql/src/schema-reader.ts` needs one function that runs a query and returns rows. It only runs `select`.
- **The search path matters.** PostgreSQL writes a name with its schema when the schema is not in the search path. A view definition then contained `test_1.orders`, and two equal schemas compared as different. The reader now puts the schema into the search path while it reads, and sets the old value again afterwards.
- A consequence: an object of another schema is always written with its schema. The trigram operator class of the bookshop appears as `public.gin_trgm_ops`.
- The columns of an index are taken from `pg_get_indexdef`, because only that form keeps the order (`DESC`) and the operator class.
- Functions and triggers are read in parts, not with `pg_get_functiondef` and `pg_get_triggerdef`, because those include the name of the schema.
- Objects that an extension created are left out. The list of extensions is read for the whole database.

### Time (M2-AC-24)

The bookshop schema on PGlite: reading one schema takes 11 to 13 ms. Comparing two models and computing a fingerprint takes 0.7 ms.

### The bookshop schema

`examples/bookshop/schema/` holds release 1.0.0 as the website shows it: the four tables and the sequence, the index on `orders`, the trigram index, the view and the trigger function. PGlite has the extension `pg_trgm`, so nothing was left out.

The file `130-reference-data.sql` of the website is not there. It fills `order_status`, a table of release 1.2.0.

### Limits

- Materialized views, partitions, collations, generated columns, exclusion constraints and `INCLUDE` columns of an index are not in the model.
- Whether a constraint is deferrable is not in the model.
- A function with a body in the SQL standard form (`begin atomic`) has an empty body in the model.

## M3

### What the generator does now

- **Names.** A name without quotes is written in lower case. A name in double quotes is kept; the quotes are dropped where PostgreSQL does not need them. A reserved word of PostgreSQL is always quoted.
- **Several steps.** `set not null` is four steps, a new foreign key with a name is two. `create index concurrently` and `drop index concurrently` are marked `-- outside transaction`.
- **`ensure column`** is a `do` block that looks at the catalog and then adds, widens, keeps or fails.
- **`upsert`** is one `insert … on conflict (key) do update`.
- **Functions.** The list is in [Functions](../migql/functions.md). A call of another function is an error of the language, not of the generator.

### Three proofs

1. The expected files are committed and compared in every test run.
2. Every expected file is parsed by PostgreSQL's own parser (`libpg-query`, 31 files).
3. Every valid example runs on PGlite on top of the bookshop schema. The change of the schema model is recorded in `migql/test/generator/effects/` and reviewed like the expected SQL. Statements that change rows have tests that look at the rows.

An example that needs more than release 1.0.0 has a file `constructs/<construct>/setup/<example>.sql`, for example the table `review`.

### Choices

| Topic | Choice |
|---|---|
| `rename column` | Generated as a plain `alter table … rename column`. The spec lists the form with a sync trigger as a non-goal, and it also demands that no expected file says "not generated yet". The plain form is correct when no older application version runs. Question 35. |
| A foreign key without a name | One step. It cannot be validated by name. |
| `references` on a new column or in `create table` | One step. |
| `ensure column` and details of a type | The length of `varchar` and `char` can grow. `numeric` is kept only if precision and scale are the same. Other types with details, such as `timestamp(3)`, are an error for now. |
| Constraint for `set not null` | Named `<table>_<column>_not_null`, as in the generation note. |
| Rows of `insert` and `upsert` | Every row gives the same columns in the same order. Otherwise the generator stops with an error. This could become a check of the language. |

### Findings

- `alter column … type` fails when a view uses the column. The example of the catalogue removes the view in its setup file. The real answer is the handling of views in the migration script.
- A failing `set not null` in four steps leaves the unvalidated check constraint behind. The next run fails at step 1, because the constraint exists. The script of the next milestone has to handle that.
- The generate run must name its test file. With the folder, the other generator tests ran in generate mode too and failed before the files were written.
