## M3.1 Exact names

- **The syntax tree holds the exact name.** The quotes of a written name are removed when the file is parsed, so every comparison of names is a comparison of texts. `sameName` in `migql/src/model/names.ts` is the one function for written names. Whether the author wrote quotes is still known from the source text; the generator asks for it in one place, for the name of a type.
- **Keywords as names.** 26 of 58 keywords can be a name without quotes. The list with a reason for each is in [Keywords and names](../migql/keywords.md); a test compares it with the grammar. `ran` stays a keyword: as a name it hid the completion of parts in the editor.
- **Types.** [Types](../migql/types.md) lists nine types. A type name in quotes is always a type of the schema. Types of several words are a gap: question 45.
- **One-line values.** `into: "Order Status"` is accepted: one name in double quotes means the same in YAML. This is the same exception as for one text in single quotes.
- **Hostile names** found one real hole: the code of `column-ensure` is a block between `$ensure$` signs, and a name that contains `$ensure$` ended it. The generator now chooses a sign that the block does not contain. A percent sign in a name is doubled in the message of the block.
- **The comparison** reports a table, a column or a sequence that is missing under one name and there under a name that differs only in case as one difference. For a table, the names that PostgreSQL derives from the table name (`Customer_pkey`) may differ.
- **M3.1-AC-11** asks for a test of a condition such as `column "Orders"."DueDate" exists`. Conditions were generated first in M4.1; the test is there (the plan tests use `to_regclass` with the quoted name).

## M3.2 Actions

- **One grammar rule for all actions.** An action is its key and a map of parameters. Which parameters an action has, and what each takes, is in `migql/src/actions/catalogue.ts`. The lexer, the checks, the completion and the YAML schema read that catalogue.
- **A flow map has keys of its own.** `{ table: customer, from: mail, not-null: true }` uses words as keys that are keywords in a statement. The lexer now reads a flow map itself: every key is a name token, every value goes to the statement lexer. This holds for every flow map, also in `rows`.
- **A type as a parameter** is written like a name or like a call: `varchar(200)`. On one line it may have no comma.
- **The removed statements are still read**, so that the error can show the action with the same content: `column-ensure: { table: orders, column: note, type: varchar(500) }`. They are not offered by completion.
- **Descriptions** are written once in `construct.md` of the action. `npm run test:generate` writes `migql/src/actions/descriptions.ts` from them; a test fails when the file is not up to date.
- **The YAML schema** is `migql/schema/migql.schema.json`, generated from the key table of the lexer and from the catalogue. All valid examples of the catalogue are accepted by it.
- **The warning under `do`** does not make an example of the catalogue invalid: the catalogue test accepts exactly this warning.
- **Website:** nine examples were changed to actions. The text around them still describes `ensure column` in two places (`statements.md`, `conditions.md`) and is left to the review.

### Found on the way

- **A check crashed on a half-parsed snippet.** The random test of M1 only parsed. It now also runs the checks, and it found the crash at once. Several checks got guards.
- **A column inside a subquery of a `let` definition was reported as an unknown condition.** The check for definitions that use themselves asked every name for its definition, also columns. It now asks only names of conditions.

## M4.1 Plan and script

### Design

- **The plan** (`core/src/plan/plan.ts`) is plain data: snippets, parts, steps, conditions as SQL with their source text, checksums. The compiler is `migql/generators/postgresql/plan.ts`.
- **The checksum** (`migql/src/checksum/checksum.ts`) is computed from the tokens of the lexer: the type of every token and, for names, numbers and texts, its characters. The parts are found in the token stream, not in the syntax tree. The committed list is `migql/test/plan/checksums-v1.txt`; the generate run only appends to it.
- **The script** (`databases/postgresql/src/script.ts`) follows "Inside the script" with one change: a step is a call of a function of the session, not a block of its own. The format is written down in [Execution and ledger](../architecture/execution-and-ledger.md).
- **The runner** (`databases/postgresql/src/runner.ts`) is 100 lines and knows markers, guards, labels and parameters.

### What a run does

- A failure is caught in the function of the step, written into the ledger with code, message, detail and context, and remembered in a session setting. Every later call does nothing. The last statement of the script raises the error.
- A part with several steps continues at the step that failed. `column-set-not-null` on a row without a value fails at step 2; after the row is corrected the next run does steps 2 to 4. This closes the finding of M3.
- `create index concurrently` that fails leaves a row "started". The next run marks it "abandoned", drops the invalid index and repeats the step. PGlite shows this; the test did not have to move to M4.2.
- A run that stopped outside a transaction leaves its row of the run as "running". The next run marks it "interrupted".

### Time (M4.1-AC-38)

The bookshop, nine snippets with 23 parts and 30 steps: loading and compiling 35 ms; the script has 30,000 characters; the first run on PGlite takes 38 ms, a second run 15 ms.

### Choices

| Topic | Choice |
|---|---|
| Baseline of the bookshop | The tests build release 1.0.0 from `101-generated.sql`, `110-views.sql` and `120-functions.sql`. The index and the trigram index of `schema/` are created by snippets. |
| Bookshop snippets | Nine snippets. The differences to the website are listed in `examples/bookshop/README.md`. |
| Search path | Question 46. |

### Limits

- The ledger has no table for batches and no state `included`.
- The log table gets one row per failure. Notices are not copied into it.
- The script was run on PGlite only: one session, no second runner, no killed run.

## M4.2 Real PostgreSQL

### The temporary server

- `startTemporaryServer` in `databases/postgresql/src/temporary-server.ts` runs `initdb` in a new folder below the temporary folder, takes a free port and starts `postgres` for connections from `127.0.0.1` only.
- **No server is left behind.** The server is the child of a small watchdog (`databases/postgresql/watchdog/server-watchdog.mjs`). The watchdog reads its standard input, which the starting process holds open. When that input ends, because of `stop` or because the process is gone, the watchdog ends the server and removes the folder. A test kills a helper process and sees both go.
- **Binaries.** First a folder named by `MIGACE_POSTGRESQL_BINARIES` (name provisional), then the package `@embedded-postgres/<platform>-<arch>`. The package is MIT-licensed and holds PostgreSQL built by zonky.io; it is about 60 MB unpacked per platform and version. Installed here: version 18.7 for Linux and Windows as optional packages, and 15.20 for Linux under another name for the nightly run. All of its versions carry "beta" in their number.
- **Driver.** `pg` 8, MIT. It is a dependency of `databases/postgresql/` because the server creates databases with it.
- A new database is a copy of a prepared one (`create database … template …`).

### Time (M4.2-AC-21)

| Step | PostgreSQL 18.7 | PostgreSQL 15.20 |
|---|---|---|
| Start a server, with `initdb` | 420 ms | 480 ms |
| Copy the prepared bookshop database | 16 ms | 19 ms |
| First run of the bookshop script | 35 ms | 43 ms |
| Second run | 16 ms | 16 ms |

All server tests together take 12 seconds: 7 for the server itself, 13 for the script.

### What the server showed

- **The same result as PGlite.** The reader gives the same canonical form and fingerprint on PostgreSQL 18 and on PGlite, and the bookshop script leaves the same model, the same notices and the same ledger rows.
- **Another major version gives another fingerprint.** PostgreSQL 15 writes the text of the view `v_order_totals` differently from newer versions. Everything else is equal. This is what the architecture note expects: one fingerprint per major version.
- **A deadlock between two runs.** The run that waited for the lock of the run kept a transaction open. `create index concurrently` of the other run waited for that transaction. PostgreSQL ended one of the two. The script now waits in a loop that ends its transaction before every pause. Found by the test with two runs at once.
- **A killed run.** The bookshop script has 60 statements. A run that loses its connection after any of them, followed by a normal run, ends with the same model and with every step done once. The same holds when the server ends the session in the middle of a long statement.
- **An interrupted `create index concurrently`** leaves an invalid index. The next run drops it and builds the index.
- **Locks.** A step that waits for a lock gives up after `migace.lock_timeout`, pauses and tries again. The limits are parameters of a run; they are listed in [Execution and ledger](../architecture/execution-and-ledger.md).
- **Roles.** The script runs as an owner of the schema that is no superuser. An application needs `usage` on the schema and `select` on the meta table.

### Choices

| Topic | Choice |
|---|---|
| Table named in a lock failure | The tables of the schema on which other sessions hold a lock at that moment. PostgreSQL does not say which lock a statement waited for. |
| Versions | The newest version (18) on every push, on Linux and Windows. The oldest supported version (15) every night, on Linux. |
| Server tests | `npm run test:server` builds first: the helper process of one test uses the compiled package. |

### Not shown

- Windows. The workflow has the job; it has not run.
- A statement outside a transaction has no lock time limit: it is sent as it is and waits as long as PostgreSQL makes it wait.

## M4.3 Client contract and Java runner

### The contract as data

- `clients/contract/cases/` holds 22 cases, one JSON file each. `case.schema.json` is their schema. `README.md` describes the contract and the format in full.
- A case has the text of a script, the parameters, the answers of a scripted database, and what is expected: the statements sent, the outcome (`success`, `failure`, `refused`), the error and the notices.
- Where the wording of an error is left to the runner, a case lists texts the message must contain (`mentions`), for example the number of a line.
- `databases/postgresql/test/contract.test.ts` checks every case against the schema and plays it against the reference runner.

### What the cases changed in the reference runner

- **Refused is its own outcome.** A text that is no script, a higher version, an unknown marker, text outside a statement and a guard without a statement throw `ScriptRefused`. The runner reads the whole script first, so nothing is sent.
- **A guard is strict.** Exactly one row with true or false. No row, more than one row or another value is a failure. Before, everything but `true` meant "skip".
- **The error carries the code** of the database.
- The script generator needed no change.

### The Java runner

- `clients/java/`: package `org.openbrod.migace`, classes `MigAce`, `MigrationFailedException`, `NoticeListener`, `Main`. Compiled for Java 11. No dependency besides the JDK.
- Gradle 8.10.2 with the wrapper in the repository; the wrapper checks the checksum of the distribution. Gradle was not installed here: the distribution was downloaded once to create the wrapper.
- 42 JUnit 5 tests. They use a scripted connection made with `java.lang.reflect.Proxy`, and Jackson to read the cases. Both are test dependencies only.
- The program: options `--url`, `--user`, `--schema`, `--param name=value`; password from `MIGACE_PASSWORD` or asked for; exit codes 0, 1, 2. All names are provisional.
- **Secrets.** Before the program prints an error it replaces the given password, a `password=` value and the password of a `user:password@` address. A test with a driver that repeats the address and the password in its message shows it.
- **On a real server.** The Java program runs the bookshop script on PostgreSQL 18.7 with the PostgreSQL driver 42.7.5. Notices, model and ledger are the same as with the reference runner.
- **One difference.** The driver puts `ERROR: ` in front of the message of an error. See open question 52.
- **Without a JDK** `node tools/java.mjs` prints that the Java tasks are left out and succeeds. The server test is skipped with a test whose name says so.

### Not test-first

The Java sources and their tests were written together and passed at the first run. The cases and the reference runner were done test-first: 13 tests failed before the runner was changed.
